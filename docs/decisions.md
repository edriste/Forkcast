# MVP decisions

- Expo, strict TypeScript, React Navigation and Supabase Auth/Postgres/Storage. Google OAuth is the primary signup/login option using PKCE and a system browser on native platforms, with email/password and OTP as a fallback. Sessions and pending invitations persist on the device. New Google users get their profile name automatically and still need to create/join a group.
- A shared theme context follows the system color scheme, using bright tangerine accents with neutral light/dark surfaces. Components consume theme styles at render time; appearance changes preserve navigation and form state. Native appearance is automatic with Expo System UI. Default map styles switch between Positron and Dark with independent optional overrides.
- The OSM migration replaces Google Places with OpenStreetMap facts, Nominatim area lookup and Overpass regional catalogues. MapLibre Native and GL JS display OpenFreeMap maps on mobile and web. Maps require no Google API keys or billing account.
- New organizations require a selected office location: explicit address lookup, selection and optional map-tap refinement. Coordinates persist with the group and its office marker remains visible without reviews or regardless of restaurant filters. Older groups reuse a valid cached center or an administrator can select one. Location lookups are authenticated, cached for 30 days and share the Nominatim gate; no autocomplete. Search-area labels are member-chosen neighborhood/city/address strings. The initial catalogue covers named food establishments within 3 km of the saved office point (or the geocoded area for legacy groups). Users explicitly search a cached local catalogue; a missing or ambiguous location is an actionable error. Administrators can update the search area; this clears only the regional search cache and retains review history. No per-keystroke Nominatim queries are made.
- Persist external OSM facts with source-qualified IDs (`osm:node:123`, `osm:way:123`, `osm:relation:123`). Facts and regional caches are separate from private group reviews. Full provider credits and the bundled cuisine-preset ISC notice live in a shared Credits & licenses dialog. Data views use one compact OSM source/license link per view. Web maps retain MapLibre’s source attribution without a duplicate external block, while native maps keep compact adjacent credits; the MapLibre browser worker/license are generated from the installed version during npm install.
- Refresh a region on the first search after 30 days. A database lease prevents duplicate refreshes for a group. Global request gates reserve at most one Nominatim request per 1.1 seconds and one Overpass request per 10 seconds per Supabase project. Failed refreshes retain the previous dataset and have a one-minute retry cooldown. Endpoints and app identification are configurable for operator-managed services.
- Overview is the default tab. Daily answers, restaurant options, votes and wheel picks belong to an organization and the Berlin calendar day. Reviewed OSM places seed options; members can nominate additional places from their own group's regional cache. Each going-out member has one replaceable vote, removed on opting out. Security-definer RPCs enforce membership, eligibility and server dates, with direct writes revoked and RLS-protected reads. Answer/vote/spin writes serialize on the organization row to prevent opt-out races. A unique vote leader is provisional; a persisted uniform wheel pick takes precedence and can be replaced by another spin. Existing cooking signup/payment remains independent. The active overview refreshes every 15 seconds and on foreground/focus changes.
- The shared tab header owns the active organization name and dropdown. Overview, Places and Cooking omit duplicate organization badges. Membership selection closes the picker, persists the group, resets screens/data for that group and preserves the active tab. Picking the current group or dismissing the menu leaves filters intact; group creation/joining remains in the team screen.
- Places owns one reviewed-place resource and one set of filters. A Map / List switch changes presentation without navigation or new data requests. The map shows office and reviewed restaurant pins, and the ranked list includes entries without coordinates and provides access to reviews when tiles are unavailable. The office pin remains independent of filters. Overview remains the default tab.
- Reviewed-place map/detail reads use saved facts and do not require OSM services to be online. Arbitrary basemap POIs are hidden. Missing cuisine is explicitly filterable as Unknown cuisine; absent hours/address/website remain absent. Raw opening-hours notation is displayed without calculating open-now status. Restaurant photo galleries are omitted; cooking-event images remain supported.
- Existing Google IDs remain marked `google_legacy`; reviews are preserved by the additive migration. Only an organization administrator can confirm a match to an OSM entry. The transactional operation moves reviews within that group only and merges histories without changing author/date/content. No automatic matching or Google metadata copying occurs.
- Every member can create/join groups and read group activity. Creators manage invitations and legacy matching. Codes are UUIDv4 values (122 random bits) with hyphens removed, valid until rotated. Installed-app invite links use `forkcast://join?code=…`.
- Organization members can supply cuisine corrections for cached or reviewed OSM places. A searchable offline multi-select uses OSM iD cuisine presets, with friendly labels mapped to exact tags and an explicit custom fallback. Known labels/aliases normalize consistently in OSM imports, overrides and filters. Existing uncommon tags are preserved. Validated multi-cuisine values are stored per organization with editor/time metadata through an RPC; RLS isolates reads and direct writes are revoked. Corrections are merged before search/filtering and detail display, survive OSM refreshes, and can be removed to restore OSM values. A separate editor link targets the exact OSM node/way/relation; users publish verified facts using their own OSM account.
- One editable opinion per member/place/organization counts toward aggregates. Review saves retain immutable versions; the current review list and ratings use only the latest version per author, including existing histories and legacy-place merges. Unchanged saves do not create extra versions. Reviews use stars and optional comments. Recommendation controls, aggregates and filters are removed; old recommendation metadata is preserved in historical rows for compatibility.
- Events use Berlin calendar dates. Organizers may participate; past events remain viewable but portion changes close. Prices use integer EUR cents. Paid lunches require a validated PayPal.me username; payment status is participant self-report and resets when quantities change.
- Every participation mutation locks the event row before checking availability. Direct table mutations are revoked. Organizers alone upload private meal/receipt images, resized to 1600px and JPEG compressed; signed viewing links last ten minutes.
- AI nutrition, background push and automatic payment verification remain deferred. Supabase deployment, SMTP and real-device acceptance require operator configuration. Public OSM services and OpenFreeMap are best-effort; free provider access does not remove separate hosting/storage costs.

- The in-app inbox is private to a recipient and current organization. Database triggers deliver cooking and payment notices in the same transaction as the underlying write. Read/dismiss operations use authenticated RPCs; direct writes are denied. Quick join shares the event-row lock and capacity checks with normal portion reservations and never overwrites existing portions/payment. Invitations expire after the meal date and disappear while joined. Payment notices reflect current debt/payment state; free lunches produce no payment notices. A shared provider responds to private live signals and refreshes on foreground, inbox opening and local mutations.

- Compact daily screens reduce repeated sections rather than shrinking typography. Attendance choices and counts share a two-column grid; a small “Spin the wheel” action sits beside voting and opens the animated wheel in a centered modal. Explicit daily nominations take priority; otherwise reviewed OSM places matching the shared Places filters are eligible. Utility actions use labeled 44-pixel icons and lists use tappable rows. Explanations and lunch participants expand on request; payment actions precede the participant list. Notification actions share a row.

- Payment-due notifications cannot be dismissed or marked as read, including through direct RPC calls or accidental privileged table updates. Mark-all-read skips them, and opening their lunch preserves the alert marker. Additive migrations restore previously dismissed/read payment reminders; payment/leave transitions still remove them. Invitations and organizer payment updates remain dismissible and can be marked as read.
- The organization screen separates office details, grouped expandable team actions and account controls. Join/create forms stay collapsed for existing members, open for initial setup, and an incoming invitation opens the join form. Form values survive collapsing; invitation controls reset when switching organizations. Credits and configured legal links share a compact account row.

- The brand fill is bright orange (`#FF8A24` in light mode, `#FFA347` in dark mode), with charcoal text on primary actions. Text/icon accents have separate contrast-safe tones. Neutral surfaces replace brown/beige chrome. Shared cards and rows have soft elevation; organization selection and active tabs use pills; focused inputs and pressed controls have visible feedback. All changes preserve the compact structure, translations and system appearance behavior.

- Saved OSM source facts refresh on detail/list reads after 24 hours, using only reviewed IDs or the selected group’s cached search IDs. Returning from the OSM editor requests source refreshes during a ten-minute window with a five-minute per-place cooldown. Service-only leases share the existing global Overpass gate and use a one-minute failure backoff. Successful source writes merge into regional search snapshots without extending their monthly discovery lifetime; failed/partial/missing objects retain saved facts. Private cuisine overrides continue to take priority; reverting an override requests fresh OSM facts.

- One live channel per active organization subscribes only to INSERT/UPDATE on small member-scoped organization signals and recipient-private signals keyed to individual notifications. Content tables and their DELETE payloads are not published by this migration. Transactional triggers cover review/cuisine/source facts, cooking/portions, daily votes and attendance, images and notifications. A 350 ms debounce coalesces bursts; resource reloads queue rather than overlap and retain visible snapshots. Backgrounding removes the channel; foreground/reconnect reloads snapshots. A minute heartbeat handles Berlin day rollover and disconnected fallback, with a five-minute safety check while connected. Routine refresh buttons are replaced by error-only retries; unsaved drafts and loaded pages survive updates.

- Lunch responses use four choices: going out, eating in the office, ordering in, and combined no lunch/away. Existing absence answers (including historical dates and older-client submissions) normalize to no lunch; ordering in has a separate count and removes a going-out restaurant vote.

- Overview previews at most three daily restaurant nominations, sorting the shared pick or unique voting leader first. The full list is searchable in a voting modal. Suggestions use a searchable saved-place modal with discovery navigation. A wheel fallback validates reviewed places within the organization and adds one selected restaurant to the shortlist. Existing automatic daily rows are preserved but hidden unless nominated, voted for or picked.
- The wheel exposes its actual candidate count and an expandable, bounded list with search for larger pools. Preview search never changes eligibility. Reviewed-place fallback shows the shared cuisine/rating criteria; users can navigate to Places to adjust them or reset them when no restaurants qualify. Missing reviews and filter exclusions have different empty messages. Explicit daily nominations retain priority over fallback filters.

- Cooking participation and daily attendance share server-side provenance tracking. New bookings select the office choice for the event date and clear restaurant votes; leaving clears only automatic attendance after the last same-day booking. Manual choices reset provenance, and an already explicit office choice stays manual. Future bookings affect only their own date; existing bookings backfill unanswered dates without replacing manual answers.

- Cooking organizers see the participant/payment roster without expanding it, with pending/paid groups and portion/amount totals. Members keep the expandable list. Paid status distinguishes participant self-report from organizer confirmation. Meal tags are an optional predefined set (vegetarian, vegan, spicy, gluten-free, dairy-free), selectable at creation and editable only by the organizer through a validated RPC; group members can read them and live cooking signals refresh all relevant screens.

- Cooking signup deadlines are optional absolute timestamps entered/displayed in Europe/Berlin. Existing lunches have no cutoff; organizer-only RPCs support changing/removing a future deadline, closing immediately and reopening. The database checks the actual clock after event and organization locks, preventing queued requests from reserving after expiry. Closed registration rejects new bookings and increases while preserving reductions, cancellations and payment actions. Quick joins share the same gate. Local deadline/midnight timers and foreground correction update visible status without server polling; existing live cooking signals cover organizer edits. Ambiguous and nonexistent DST times are rejected rather than guessed.

- Organizer payment confirmation is authoritative for the current portion amount: a validated organizer-only RPC locks the event/booking, checks the displayed portion count, sets paid plus a confirmation timestamp and privately notifies the participant once. Confirmation clears unpaid and redundant organizer payment alerts; the participant sees no further payment action. Self-report undo cannot reverse confirmation. Portion changes reset both paid and confirmation, preserving the existing amount-change rule. New booking inserts notify the organizer, excluding their own booking; updates do not repeat signup alerts and cancellation removes them. Notification visibility remains membership/recipient scoped and existing private live signals deliver both new kinds.

- Restaurant favorites are personal and organization-scoped, writable only through a validated RPC for group-observed OSM restaurants. Reviews are optional. Owned favorites and explicit shared nominations keep external facts accessible after regional-cache eviction; another member's private favorite is not eligibility until the restaurant is nominated. Public fact-read policies and the Edge Function apply the same boundaries. Each favorite has its own recipient-private refresh signal, avoiding broad shared write locks or publishing bookmark rows. The app shares favorite state across details, reviewed lists, a Favorites view and overview quick nominations; authentication/organization changes reset it. Bookmark removal never removes a shared nomination, and favorites do not automatically bias the wheel.

- Organization membership has explicit `admin`/`member` roles. The additive migration promotes existing creators, and both creation RPCs create an admin membership. Joining always defaults to member and never downgrades an existing role. The original `created_by` is historical only. Admins can manage invitations, locations/search areas, legacy place matching and roles; event organizer permissions remain independent. Role changes and every admin mutation serialize on the organization row and check current authority after the lock, preventing concurrent last-admin removal and queued actions from demoted users. Membership writes are RPC-only, all members can read their own group's roster, and existing organization signals refresh roles automatically. The UI supports handing over administration but disables demoting the last admin. Service-role maintenance bypasses client permissions and must preserve at least one administrator when deleting accounts directly.

- Member management revokes membership rather than deleting authored content or cooking/payment history. Admins can remove other members, while self-departure has its own RPC. All departures/removals serialize with role changes on the organization row and protect the last admin. Removal rotates the shared invite code; voluntary departure leaves it valid. Joining revalidates invitations after locking, and existing lunch mutations recheck membership after queued organization locks. Tiny per-account membership signals have own-user RLS independent of group membership, so revocation reaches the affected user without exposing private DELETE rows. Active group subscriptions include this signal; the no-group screen uses a single account subscription. The client drops a successfully left organization immediately, persists the fallback selection and clears stale invitation codes. The roster uses compact rows with administration dialogs and explicit removal/leave confirmations, with English/German copy explaining retained records and invitation rotation.
